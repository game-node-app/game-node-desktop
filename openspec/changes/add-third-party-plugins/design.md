# Design

## Context

See proposal.md for motivation and scope. Observed at base `5e9a882`:

- `crates/plugin-protocol/proto/plugin.proto` defines PluginHost.OpenSession/SubmitDiscovery and ProviderHost.Exchange/GetContext/Account/Secret/Login/DeclareActions. Discovery/catalog/counter/status/results also travel through Exchange; these are not separate unary endpoints.
- API is 1.3 with minimum minor 1. `capability.rs` lists 13 base grants and optional `ui.settings`; SDK maps transport failures to coarse errors, including `Denied`.
- `crates/app/src/plugin_host.rs` uses static official descriptors; services, login policy and credential aliases are trusted composition. `ProviderProcesses` supervises local executables. Transport is an owner-restricted Unix socket or Windows named pipe, not a public TCP server.
- The Rust SDK/protocol inherit workspace GPL-3.0-only and publish=false; the SDK is already separate from Core. Public protocol also contains Rust domain DTOs and validation beyond generated bindings.
- `PluginInventory.tsx` already distinguishes official/community and exposes native-access declarations but currently lists only official inventory. Settings uses async Tauri commands and React Query.
- Existing local-game code keeps multiple WatchRoot entries and supports explicit file/folder save paths; backup preview currently depends on its packaged engine. New location/profile services must not silently equate missing engine support with absence of files.
- The Steam integration has been consolidated in main `desktop-plugins`, `desktop-plugin-services` and `desktop-providers`. These specs establish the official plugin baseline, including packaged external executables, descriptor-scoped scanner/catalog/counter backends, cached-data preservation and no in-process Steam substitute. The code observations above remain tied to `5e9a882`; spec synchronization alone does not establish native acceptance.

This change follows the Steam migration and evolves its consolidated contracts. Narrow the prohibition on user-writable manifests only for distinct identities installed through the managed third-party flow; bundled identities and descriptors remain authoritative. Preserve the integration's surviving scenarios in modified requirement blocks, including missing/incompatible Steam executables and valid/unauthorized registered backends. Third-party detected executable targets and approved custom overlays extend the host's launch paths without changing official plugin implementations, credentials or default actions. The Steam integration's outstanding native acceptance stays with that change and `docs/steam-plugin-integration.md`; this proposal neither completes those checks nor repeats that migration. The Linux package-manager change remains a separate official-plugin compatibility constraint.

## Goals / Non-Goals

**Goals:** Define one language-neutral public API; additive third-party registration and controls; deterministic package trust, consent and compatibility; broad but bounded Core service coverage; runnable independent Go and SDK Rust examples.

**Non-Goals:** OS sandboxing, security certification of native executables, marketplace/ratings, plugin code embedded in the GameNode frontend, native DLL loading into Core, generic Tauri invocation, unbounded shell/SQL APIs, changes to official plugins or their current grants and behavior. Plugin-owned windows can use their own native or web UI technology.

## Decisions

### 1. Separate managed third-party registration

Keep static official descriptors authoritative and introduce an external registry with immutable validated package descriptors. Do not infer official status from a manifest or publisher-supplied flag. Reserve all official plugin/provider IDs and `org.gamenode.*`. Manifest kind is `provider` (one separately validated provider id compatible with existing `<provider>:<game>` keys) or `extension` (no owned provider). Extensions use authenticated plugin identity plus explicitly scoped target-game handles, never impersonate the target provider, and can offer launch recipes for official or third-party games. Reject collisions before executing a package. Register backends through Core's existing domain registry without importing SDK into Core or SDK into the host.

Extend app host composition through new external modules rather than changing Steam/PackageKit implementations, manifests, login policies or credential aliases. Official packaging and startup remain valid without an external registry. Third-party disable/failure preserves library history and previously reconciled facts; provider actions become unavailable until enabled. External accounts and secrets are namespaced by publisher fingerprint/plugin/provider/profile; they cannot select Steam or GameNode physical slots.

Alternative: scan arbitrary directories at startup. Rejected because it executes dropped files without explicit installation or consent.

### 2. One public wire protocol, optional SDK

Keep existing protobuf package and field numbers compatible. Add third-party features at API 1.4 through new services/messages and optional fields. Preserve official 1.1–1.3 negotiation and old SDK methods. Separate the independently distributable `.proto` contract plus normative transport/lifecycle guide from Rust convenience models. Add optional structured SDK errors without breaking official callers' current Error matching; new detailed client methods expose denial metadata while old conversions retain their existing behavior.

Third-party handshake advertises an explicit supported major/minor range plus required/optional feature IDs. Select the highest mutually supported minor, never a higher version than either declares. Add `DescribeApi`, `GetPermissions`, `WatchPermissionChanges` control RPCs available to authenticated enabled plugins without a user-granted data permission. Service methods below are proposed names, not existing endpoints. The reference docs must label existing versus added methods and show which Exchange messages implement each provider operation.

Alternative: SDK-specific protocol or mandatory Rust SDK. Rejected because independent clients must have equal access and compatibility guarantees.

### 3. Persistent API grants and revocation

Effective authorization = host-supported permissions intersect validated manifest requests intersect saved user grants, further constrained by platform, resource scope, profile/session/operation epochs and current grant revision. Separate required/optional requests; installation defaults disabled and data grants default denied. Required denial blocks dependent provider work, but the authenticated control session can report missing permissions. Optional denial permits documented degraded behavior. Unknown required permission rejects activation; unknown optional permission is returned unsupported and never granted. Plugins cannot change grants themselves.

Save grant changes atomically, then publish the new revision and notify the plugin/UI. On failure leave the old effective grant and control state. Recheck authorization at the side-effect commit point, including after queued work or user confirmation. Cancel work affected by revocation, close relevant login resources and refuse subsequent calls with explicit denial. Do not erase previously successful facts on denial/cancellation. For operations already committed, report the completed effect honestly; revocation cannot undo filesystem work. Disabling persists state, revokes sessions immediately and stops the supervised process tree with a bounded grace period; isolated unsandboxed processes may evade supervision, which must be disclosed.

Use gRPC PERMISSION_DENIED with safe structured details: reason (`not_granted`, `revoked`, `scope_denied`, `required_permission_missing`), permission ID and grant revision; no secret values or arbitrary paths. Unauthenticated/stale/unsupported/invalid/unavailable remain distinct statuses. Streaming submissions receive a correlated failed operation result, never an accepted empty snapshot. SDK exposes typed errors and examples present actionable messages without raw transport text. Rate-limit audit records to plugin/method/permission/reason/time, excluding values, tokens and cookies.

#### Creator scope and explicit resource delegation

Read/write/delete are independent for shared runtime, library-root and save-profile records: List/Get/Watch require the read grant, Create/Register/Update and root additions/updates require write, and Remove/RemoveRoot require delete. These replace the previously proposed broad configure grants, not any existing official capability. Installing a plugin grants none of them; own-creator scope is a scope choice after consent, not automatic permission. Host identity assigns creator and owner; a caller cannot obtain own scope by supplying a different plugin id.

Example: Dolphin's plugin may update or delete its own “Dolphin external HDD” registration and create “Dolphin SSD C:” with approved write/delete, but cannot change “RetroArch SSD NVMe” without an explicit resource grant. Prefer updating an existing installation path to preserve its resource id when appropriate. Removal affects registrations/bindings only, shows affected games and preserves ROMs, game history, saves and archives. Cross-owner grants show creator and recipient identity/version, exact records, selected fields/operations and revision; revocation fences queued commits. They do not transfer creator ownership. Selected-record grants do not expand to new records; explicit category grants cover eligible published records within the category scope. Private namespaces, credentials, official descriptors and foreign provider account/discovery facts remain excluded. storage.persist intentionally permits own retention/cleanup without storage.delete; Storage.Delete still checks storage.delete and no cleanup API accepts a foreign namespace.

### 4. Initial host resource catalog

Retain existing grants and provider contracts. No grant implicitly authorizes all operations or categories; an explicit category scope covers only its eligible published records. Unless explicitly described otherwise, resource mutations target the caller's provider entries; global reads need a separately granted `library.read.all`. Runtime, library-root and save-profile records use independent read/write/delete grants initially scoped to records created by the authenticated plugin. Users can extend each operation to published foreign domain resources by category-wide or selected-record grants; creator provenance remains host-owned and updates record the acting plugin. Launch/save/location/file access is scoped separately and never permits foreign provider account/catalog mutation, credential access or foreign private-persistence cleanup. All advertised supported methods must be operational, not successful stubs. This delivery includes the data plane: authorized publication, session retention or consented persistence, query and inter-plugin subscriptions. Core-side collection tools, diagnostic interpretation, FPS capture, prediction algorithms, dashboards and external profile publication are future consumers, not required implementations here. Platform-specific absence is returned explicitly. API metadata publishes introduction minor, risk, scope, availability and required grants for every method.

### 5. Package format and publisher trust

Use `.gnplugin` ZIP packages with root `plugin.json`, `integrity.json`, `signature.ed25519`, `licenses/` and `bin/<target>/...`. Manifest schema 1 has stable reverse-domain plugin id, plugin kind, provider id for provider-kind packages, display name, SemVer plugin version, API range, required/optional capabilities with scopes/reasons, supported target triples and relative entrypoints, publisher public key/key id, SPDX expression or `LicenseRef-*`, bundled license/notice paths, optional source URL and optional HTTPS update URL. It also declares configuration modes (`external`, `declarative`, or neither), preferring external when both are present. Include validated provider/login/action policies as hashed resources. Schema rejects unknown security-relevant fields and invalid bounds.

Integrity schema 1 maps every payload file (including raw manifest and license bytes) to SHA-256; the integrity file itself and detached signature are excluded to avoid circular hashing. `signature.ed25519` contains the raw 64-byte Ed25519 signature over the exact `integrity.json` bytes, prefixed by the ASCII bytes `GameNode/.gnplugin/integrity/v1` and one NUL byte (`0x00`), with no newline. This domain separator scopes the signature to GameNode plugin integrity schema 1; the JSON is not parsed or reserialized before verification. Reject duplicate JSON keys and ZIP entries, absolute/traversal/drive/UNC paths, case collisions, symlinks/hardlinks/reparse points, devices, unlisted payloads and architecture mismatch. Bound initial packages to 256 MiB compressed, 512 MiB expanded, 4096 entries and 4 MiB metadata; reject overflow during streaming extraction. Only the selected target's executable is launched, with validated worker-side executable permissions and no archive hooks.

A first package is self-signed and untrusted until the user confirms publisher fingerprint and native-code warning; a valid signature proves possession of that key, not publisher reputation or safe code. Pin the key to installed identity. Later packages require the pinned key. Key changes are blocked pending a separate explicit publisher re-trust flow; no automatic rotation in v1. No permission or official status is inferred from signatures.

Store immutable versions under DataPaths data_dir/plugins/<id>/versions/<version>/<target>, with registry state and active pointer committed atomically. Per-user permissions/ACLs, hashes checked before launch, no PATH search. Hash verification does not protect against a malicious process running as the same OS user; describe this limit. Install validates before executing and presents exact license and requested grants offline.

#### Target requirements and host environment assessment

Each signed schema-1 target binds OS, executable architecture/ABI and relative entrypoint to typed optional requirements. Use explicit target tuples, never Cartesian products of OS/architecture lists. Windows requirements support numeric version/build bounds and client/server product; Linux supports libc family/minimum version and optional distribution id/version allowlists. Unknown required selectors, invalid bounds, ABI contradictions and ambiguous target matches are validation errors. Requirements within one target are ANDed; distribution allowlist entries are ORed. Define deterministic target selection, rejecting unresolved ambiguity instead of silently choosing an arbitrary binary. Emulation is disabled unless explicitly supported by host policy and verified for the selected executable.

Keep required constraints separate from optional author-tested environments. If a distribution allowlist is omitted, any distribution satisfying the other requirements is eligible. Distribution names do not stand in for libc compatibility. An unlisted tested environment is an informational coverage gap, not a mandatory failure. Compare OS/libc numeric versions by documented components; distribution constraints use documented distro-specific ordering or exact strings, not a blanket SemVer assumption.

Illustrative manifest fragment (values demonstrate declarations, not inferred requirements for actual binaries):

```json
{
  "targets": [
    {
      "os": "windows",
      "arch": "x86_64",
      "abi": "msvc",
      "entrypoint": "bin/windows-x64/plugin.exe",
      "requires": {
        "windows": {
          "product": "client",
          "min_version": "10.0",
          "min_build": 22000
        }
      },
      "tested_on": [{"product": "windows-11", "release": "23H2"}]
    },
    {
      "os": "linux",
      "arch": "x86_64",
      "abi": "gnu",
      "entrypoint": "bin/linux-x64/plugin",
      "requires": {
        "linux": {
          "libc": {"family": "glibc", "min_version": "2.36"},
          "distributions": [{"id": "debian", "versions": ["13"]}]
        }
      },
      "tested_on": [{"distribution": "debian", "version": "13"}]
    }
  ]
}
```

Core/platform owns the minimal detector required to assess these constraints before any candidate plugin executes. Do not depend on a detector plugin to decide whether other plugins can start. An optional official diagnostic plugin may enrich user-facing diagnostics later, but cannot override host eligibility. This is narrow execution compatibility detection, not the plugin-produced hardware telemetry/diagnostics collection described elsewhere.

Detect the effective execution environment: Windows actual version/build/product and supported executable architecture; Linux os-release ID/VERSION_ID, relevant libc family/version and ABI. ID_LIKE is diagnostic ancestry, not inherited distribution support. Where GameNode is isolated, identify the userspace in which its supervised plugin actually runs; do not substitute surrounding-host kernel/CPU facts for userspace dependencies. Perform blocking probes on workers, without candidate code, package-supplied commands or installation hooks. Detecting a bundled runtime must not execute it as a pre-validation probe. Unknown facts remain unknown; the detector does not promise arbitrary shared-library/dependency completeness.

Return a typed verdict and reasons with required/detected values: compatible when all mandatory checks pass; incompatible for a known mandatory mismatch; otherwise indeterminate for unresolved mandatory facts. Tested-environment coverage is a separate informational field. Only compatible targets proceed to ordinary integrity/API/grant/activation checks. Re-evaluate during validation, update selection/activation and before each supervised launch with refreshed relevant facts. An installed package failing new checks remains inactive with preserved data/history. Existing unsupported-architecture import rejection remains unchanged. A failed candidate update cannot restart a now-incompatible previous version. Never fall back to another unapproved entrypoint, shell or assumed emulator.

Settings shows target, effective environment, verdict and precise failure/unknown reasons in en/pt-BR, separately from author test coverage. Compatibility is eligibility under declared requirements, not a guarantee of execution success or safe behavior. Interpreted plugins must account for their interpreter/native dependencies; this addition does not authorize Python provisioning or executable installer hooks.

Detection references: [os-release](https://www.freedesktop.org/software/systemd/man/250/os-release.html), [Windows version detection caveats](https://learn.microsoft.com/en-us/windows/desktop/sysinfo/targeting-your-application-at-windows-8-1), and [Python platform compatibility tags](https://packaging.python.org/en/latest/specifications/platform-compatibility-tags/).

### 6. Updates and recovery

Initial distribution is user-selected local packages plus per-plugin update feeds, not a central marketplace. Signed update indexes carry schema, plugin id, monotonically increasing sequence, expiry, SemVer releases, target/API ranges, HTTPS package URLs, sizes and package hashes. Verify with the pinned publisher key; remember highest sequence and reject replay/expired metadata. Revalidate redirected URLs and downloads as in Network.Fetch. Check manually or once per 24h while app runs after user opts into checks; checks/downloads do not execute plugin code.

Updates are manually approved in v1. Compare permissions, scopes, native declarations, license, publisher and API requirements before activation. New/wider scopes or required grants remain denied until approved. Stage and fully verify, stop/fence old sessions, atomically swap the active version and perform bounded readiness check. Retain last-known-good version; failed activation restores it with the current grants intersected with its own manifest, never historical broader grants. Persist transactions for recovery after interruption. No install scripts or automatic plugin data migrations; SDK storage contract stays compatible, schema-changing plugin data must use versioned keys and must not destroy fallback data. User-requested downgrade uses the same verified package path and a warning; update feeds cannot silently downgrade. Removal stops sessions and removes package/grants; keep saved library facts and offer separate deletion of plugin-private config/secrets.

### 7. Third-party API version policy

Third-party minimum starts at API 1.4. Major changes are incompatible unless an explicit adapter exists; v1 includes no cross-major adapter. Support old third-party minors within the current major for at least 12 months after their successor release and at least the last two released minors, whichever window is longer. Publish release dates and support floor through metadata and docs. Additions are optional/minor; changed meaning/removal requires major or documented adapter. Keep official API 1.1–1.3 support outside this retirement policy.

Older supported plugin: negotiate its older minor, omit newer optional features and expose documented feature-unavailable behavior. Newer plugin: negotiate a lower overlap and disable optional unavailable features. Missing required feature/no version overlap: do not start provider work; keep package/data installed and show actionable incompatible status. Never substitute an older API that grants broader access or silently skip security checks. Host upgrades re-evaluate installed packages; failure leaves official providers usable.

### 8. MIT public assets and two real examples

Set explicit MIT license boundaries for SDK, public protocol definitions/Rust crate and examples, preserving host/Core GPL-3.0-only and third-party notices. Verify authority for each covered file before changing notices; if permission is unavailable, isolate/rewrite the affected public implementation and do not publish it as MIT. Prepare standalone versioned SDK/protocol source archives with dependency versions and lockfiles, independent of workspace path dependencies; registry publication is a separate release action. SDK package version is distinct from wire API version.

Place examples under `examples/plugins/rust-sdk` and `examples/plugins/go-grpc`, each with separate IDs, manifest, license, build/package/run README and fixture data. Rust uses the public SDK without internal crates. Go consumes only the public `.proto` release and generated bindings; `grpc.WithContextDialer` uses net.Dialer for Linux Unix sockets and go-winio.DialPipeContext for Windows named pipes, isolated by platform build tags. These are transport helpers, not a GameNode SDK. No TCP proxy or Rust bridge is required.

Both kinds of plugin use the same public contract; extension sessions omit provider ownership and receive separate target-game contexts rather than another provider's ServiceContext. The examples include a provider discovery mode and a launch-extension fixture profile. Both implement OpenSession, readiness and Exchange commands/results, GetContext, fictional discovery, catalog chunk/completion and counter output, cancellation/shutdown, one permission-protected request, deliberate denial and negotiated feature fallback. Supply opt-in recipes or fixture-host cases covering every existing RPC and settings operation, including fake account/secret/login/action flows; never reuse real Steam credentials or make destructive calls by default. Include at least one new Core service read and a confirmed write recipe. Both also include detected URI/executable launch and custom argument/environment/runtime-wrapper recipes, with denied access, cross-provider approval and missing-runtime cases. Use fixture executables and opt-in real-launch instructions; no default launch of installed games. Both examples demonstrate opening/focusing/closing an actual plugin-owned configuration window and saving one non-secret preference; fixture tests cover protocol behavior while native acceptance covers real windows. Direct calls and SDK methods are mapped to the same service/method/messages. Samples are runnable plugins, not pseudocode; assertions compare wire results against the same host contract.

Protocol guide defines raw credential decoding, endpoint interpretation, deadlines, ready/command/result ordering, backpressure, cancellation, epochs, error details, limits and package signing. No secret values in logs. Fixture host makes OS-dependent login deterministic; real native transport acceptance remains required on each OS.

### 9. Settings and license disclosure

Extend current Stores PluginInventory rather than add a new settings navigation topic. Provide Install, Enable/Disable, Configure, Permissions, Check updates, Review update and Remove. Async commands plus React Query snapshot/cache updates keep host grant revisions authoritative. Use existing Tailwind/theme tokens, Mantine controls, AppModal for confirmations and FloatingModal for substantial license/detail work surfaces inside GameNode. All statuses and disclosures work by keyboard and in pt-BR/en; plugin names are untrusted text, no HTML. Plugin-owned windows manage their own UI and do not join GameNode's modal/focus stack.

Show requested/granted/effective permissions separately, scopes, API-enforced versus native declarations, read/write/execute/destructive effects, publisher fingerprint, platform, versions, compatibility, license expression/full local text and source link. Before first enable and after native declaration changes, explain that third-party code is independently maintained and runs with the user's OS privileges, can access files/network/processes directly beyond API grants, and disabling host access cannot undo changes or guarantee termination of escaped children. Do not label native declarations a complete observed access list.

Validate SPDX syntax/LicenseRef text presence, included dependency notices and public-only example dependency graph. Proprietary license metadata is allowed at the process/API boundary; do not reject it solely because Core is GPL. Missing notices/manifest claims are actionable validation errors; a manifest cannot prove license compliance or absence of copied Core code. Documentation describes author responsibilities and avoids a legal-certification badge.

### 10. Plugin-owned configuration with optional declarative forms

GameNode owns operational administration; functional configuration belongs to the plugin. Prefer an external configuration window when declared and granted through new optional `ui.configure` (API 1.4). Keep existing `ui.settings` as an optional convenience with unchanged semantics and no mandatory JSON UI schema for external windows. A plugin may offer either, both or neither. If external configuration is denied or unsupported, offer its declarative alternative only when independently declared and granted; otherwise show an actionable unavailable state.

Configure is an explicit host UI action, not a plugin-controlled request to spawn arbitrary executables. It sends a host-issued Open configuration command through the supervised process's authenticated Exchange stream. The verified plugin entrypoint owns its UI, using its chosen native toolkit or its own web renderer; the host does not load plugin HTML/JavaScript into a privileged GameNode view or open arbitrary plugin-supplied URLs. UI helpers, if any, are declared hashed package files supervised as descendants of the plugin process. No separate unauthenticated bridge is introduced.

Correlate Open/Focus/Close commands and opened/focused/closed/unavailable/failed results using session, profile epoch, operation id and an opaque configuration handle. Allow one configuration window per plugin/profile session. Repeated Configure focuses an existing window; closed notifications clear the handle. Bound command acknowledgement waits to five seconds, without treating a long-lived open window as an unfinished blocking RPC. On profile change, disable, update, removal or ui.configure revocation, request close and fence all old contexts; disable/update/removal also stop supervised plugin processes. An acknowledgement failure is visible and cannot block unrelated settings or cause repeated automatic UI launches. A native window may outlive a misbehaving process tree; existing unsandboxed-process disclosure applies.

No configuration window inherits Core privileges, authentication or permission-administration authority. It reaches host data only through the plugin's authenticated, scoped API context; the plugin can service provider commands concurrently while a window is open. Store ordinary preferences in plugin-private versioned storage through granted storage APIs (or plugin-managed native storage subject to the native-access disclosure), and secrets through scoped Secret APIs. Saving configuration never grants extra API access. Third-party code is responsible for its own UI validation and accessibility; public docs and examples demonstrate keyboard navigation and responsive background work.

Alternative: rich plugin UI embedded inside GameNode, or mandatory declarative forms. Embedded UI increases privileged frontend exposure and imposes a web framework; mandatory forms restrict complex workflows. External windows preserve language/toolkit independence while keeping trust controls in GameNode.

### 11. Standard launch and per-game custom launch overlays

Use the exact public permission IDs `game.launch` and `game.custom_launch`. They are independent grants: normal requests require game.launch; a custom request requires game.custom_launch and an approved recipe, without implicitly granting normal launch. Neither grants discovery, broad library reads, installation, file modification, downloading runtimes, or access to another plugin's credentials. The ordinary user's Play action remains a host operation rather than requiring the originating official plugin to request either new third-party permission.

A detected target is a typed URI or local executable attached to an installed game/installation revision. Discovery can originate from a third-party provider or an existing host/official/manual detector. Provider packages submit their own candidates through the discovery lifecycle; the host validates and, for executable targets, records initial user approval. Treat executable registration as part of authorized own-provider discovery, not an additional public launch permission. Preserve official URI-only DeclareActions bytes/semantics and introduce a separate additive detected-target message instead of widening an old field.

A local target contains an approved installation-root handle, executable path relative to that root, argument vector and working-directory handle/path. The host validates canonical paths and file identity/executable type using background workers, including symlink/junction replacement checks. Revalidate before each spawn, bind the stored approval to a target revision, and show a repair choice when moved/missing. Approval for a detected executable is not implied merely by library.discovery. Main provider-spec requirements that currently restrict all executables to manual must explicitly permit this managed path; official static manifests remain unchanged.

`game.launch` accepts only game/installation id plus expected detected-target revision, resolving existing parameters on the host. Attempted argument, environment, working-directory, URI or executable overrides are invalid and never silently accepted. A plugin may request normal launch of a user-approved game from any detection source. A user-selected per-game handle exposes just the target information necessary for that grant; enumerating the whole library still requires library.read.all. Normal launch uses the source-detected target, not a selected custom overlay.

`game.custom_launch` permits replacement or wrapping of that target. A plugin proposes a versioned recipe containing game/installation id, expected base-target revision, typed alternate target or runtime executable handle, argv tokens, working-directory handle, environment set/unset map and runtime/prefix handles when applicable. Wrapper composition is structured: executable/argument tokens refer to approved runtime and game handles; no shell string, shell expansion, elevation or provider-credential access. Runtime binaries may live outside the game folder but require their own explicit approved handle. Environment names/values are bounded, validated per OS and never passed as command-line shell fragments. Start children with a documented game-safe OS environment plus approved overrides, excluding host/plugin session credentials; environment-based loader/injection effects are disclosed as executable-code authority.

This permits a Linux plugin to recommend a Proton build and prefix for a Steam, Epic or local executable, or select an identified game executable to bypass a publisher launcher where the game supports direct execution. It does not make launcher-dependent authentication, DRM or missing game/runtime files disappear. The host API launches installed approved targets; runtime installation uses a separately approved installation workflow. Prefix-writing effects belong to executing the approved runtime and must be shown, not treated as files.write enforcement over native descendants.

Custom recipes are plugin-owned overlays keyed to a game/installation/profile and recipe revision; do not overwrite the original provider's launch metadata or official Steam configuration. Selecting another provider's game is launch authorization only, not permission to publish its discovery/catalog/account state. Keep matching/favorites/history/playtime identity attached to the original game. Process attribution follows the launched runtime/child game and host policies; a URI dispatch or successful process spawn is not proof that gameplay started. Preserve existing playtime-source policy and do not fabricate provider playtime counters.

Review executable/runtime paths, argv, working directory and environment effects once when approving a recipe and selecting it for Play. Only one recipe can be active per game/profile; users can select the detected default. The host resolves the selected approved recipe when the user clicks Play, so no second prompt is needed for every unchanged launch. A plugin-initiated launch needs an explicit correlated host confirmation unless it redeems a one-use host-issued user launch intent. Changes to executable/runtime, base-target revision, arguments, working directory, environment or resource scope invalidate the corresponding approval. Recheck grant/approval/identity at spawn. Disable/revoke/delete makes dependent recipes unavailable and preserves the default target; offer Use detected default explicitly rather than silently launching a different route. Host-spawned game/runtime processes are tracked separately from the plugin supervision tree. Already-running games are not killed by permission revocation or plugin removal.

For custom URI targets, environment/working-directory/argv overrides cannot be reliably applied to an already-running OS URI handler. Reject requests claiming those semantics with an explicit unsupported-target error; require direct executable/runtime launch to guarantee them. Never silently drop requested environment changes. Existing `InstallationHost::launch_with_environment` has a legacy default that ignores environment; the new custom path must require an adapter that can honor all requested fields and fail explicitly otherwise, leaving old official behavior untouched.

Alternative: have a plugin spawn the game and report success. Native code can do that outside API control, but the supported host path retains user intent, shared launch errors and process attribution. Mutating Steam provider metadata or faking a provider identity is unnecessary and prohibited.

### 12. Save profiles and common filesystem/storage inspection

Extend the current local-save profile model through a generic game/installation plus save-context identity; do not fake manual-provider entries for Steam/other games. Existing code already supports a list of watched directories (`WatchRoot`) and explicit file/folder save configuration, but current packaged backup execution is Windows-oriented. Profile CRUD and filesystem inspection are available independently of the backup engine; real create/restore requests report platform/engine unavailability rather than claiming newly implemented Linux backup support. Save profiles/history remain independent of GameNode catalog rematching and account sign-in.

Create/UpdateProfile proposes a revision with multiple scoped file/directory resources, bounded relative include/exclude rules, emulator-user/prefix context and shared-resource markers. A host preview and user approval activates it; expanding roots invalidates approval. Plugins edit their own contributions by default. Selected foreign profile edits require separate explicit resource/operation grants and retain original provenance; selecting another source's profile does not itself authorize editing that source. RemoveProfile removes/deactivates the contribution but preserves archives. Jobs freeze revisions; edits invalidate obsolete jobs without relabeling old history. Shared emulator memory cards must be identified, preview their full restore impact and serialize writes by backing resource. Check emulator/runtime activity before copying/restoring instead of assuming that a game-content exit closed the emulator. Configuring paths does not grant backup/restore or raw-file access.

All location endpoints address approved opaque resource handles and revisions, for game installation roots, save resources and runtimes alike. GetSize reports logical bytes and selected file counts, deduplicating overlapping logical paths; it does not pretend to report allocated disk usage. GetAccess distinguishes read-only attributes/mode metadata from effective readable/writable/create/delete states (allowed/denied/unknown) under the current OS user, including ACL/parent constraints. Do not modify files or permissions to test access. GetLastModified reports per-entry OS timestamp/resolution and newest selected entry separately from root directory mtime; absent/unknown values are not zero timestamps.

GetFingerprint streams SHA-256 per file and a versioned tree fingerprint. Tree input is sorted relative UTF-8 path bytes, entry type, logical size and content digest, encoded unambiguously with lengths; include empty directories, preserve case and distinguish additions/deletions/renames (rename can be reported as removal plus addition). Files with unsupported path encoding produce explicit partial status. Dates and permissions are metadata, not content-hash inputs. Fresh comparisons reread content and do not infer unchanged bytes solely from size/mtime or a cached digest. Compare accepts compatible inspection snapshot IDs with the same scope/filter/algorithm/revision, returning changed/unchanged/indeterminate/incomparable and per-entry outcomes. A hash change proves different bytes, not semantic corruption or malicious content.

Traversal/hashing runs on bounded cancellable workers/jobs with progress and per-plugin concurrency/IO quotas. Revalidate handles and before/after file identity/size/mtime and enumerations, retry only within limits, and mark changing/unreadable/missing files partial or unstable. No full-set unchanged verdict is allowed after any incomplete/unstable read, profile revision change, disconnected storage or unknown scope. Results carry observed start/end and consistency=best_effort; this version does not promise an atomic filesystem snapshot. If a writer/game is active, report that condition and do not certify a quiescent save snapshot. Large game directories are hashed only on explicit request, optionally selecting files; metadata/availability queries never imply a complete hash pass.

Locations.Inspect returns availability (available/unmounted/disconnected/inaccessible/missing/unknown), volume identity token, mount point, local/network, internal/external/removable/unknown, bus (USB/SATA/NVMe/other/unknown), media (HDD/SSD/other/unknown), capacity/free bytes and evidence/time. These are separate dimensions: a USB drive may be an HDD or SSD. A network location's remote physical medium remains unknown unless explicitly reported by a collector. Use platform metadata on workers and preserve unknown values; do not derive SSD/NVMe certainty from a path label, run benchmarks or require elevation. Expose only opaque device identities by default, not hardware serials.

WatchAvailability emits bounded debounced typed events to Core and authorized plugins. Bind approved roots to a volume identity plus relative root where available. If an external/mapped volume disappears, pause related work and show a localized unavailable state; preserve games, profiles, history and last observations rather than reconcile as empty/deleted. A different disk at the same mount point does not inherit approval. Reconnection of the same identified volume can restore availability after scope revalidation; ambiguous identity requires review. Never create a replacement source directory on the underlying filesystem while the intended mount is absent. Media type alone is not a diagnosis of poor performance.

#### Save formats and future runtime-specific save management

A plugin declares its emulator's approved save locations and naming rules, which may be unrelated to the ROM directory. Several runtime-specific profiles can refer to one GameNode game/content. Record optional artifact kind (in-game/battery save, save state or shared container), format id/version, expected byte-size constraints, content/ROM variant binding, runtime/core and version, producer provenance, naming pattern, slot and supporting files. A .sav extension or 128 KiB size is not a universal format/compatibility guarantee. Raw in-game saves and serialized emulator states have separate compatibility declarations. Example source: the Libretro VBA-M guide distinguishes its .srm container from plain .sav and documents conversion: https://docs.libretro.com/library/vba_m/#directories.

Compatibility is plugin-attributed evidence with compatible/conversion-required/incompatible/unknown outcomes, supported source/destination runtime versions and limitations. Content changes/patches require re-evaluation; never truncate, pad, rename or reinterpret bytes solely from extension/size. Backup manifests should retain known format, source runtime/version, content binding, hashes and conversion lineage without relabelling old backups after a runtime change.

Future capabilities may list available saves with name, logical size, created/modified times, last-loaded observation, screenshot/thumbnail, profile/device/card and platform-specific slots. Fields are optional, bounded, permission-scoped and attributed; unknown creation times remain unknown. Last-loaded is an observed/reported event, not inferred from mtime. Distinguish a save-associated captured image from illustrative artwork. Screenshots are approved bounded byte/resource references, decoded off the UI thread; descriptive metadata grants no new file access or persistence.

A container can be an individual file, directory set or virtual memory card with entries for several games. Plugins interpret platform layout and slot semantics; Core need not contain PS1/PS2 card or console-storage parsers. Whole-container backup/restore or conversion must disclose all affected games and serialize backing-resource writes. A selected game does not authorize modifying other entries on its shared card.

When supported in a later negotiated capability, the user may select a save per game/runtime. The plugin states whether it can load it directly or needs import, a particular filename/location, or conversion. Plan first, review permissions and affected resources, back up originals, produce and validate new output, then select the resulting profile; preserve originals and provenance on failure. Conversion tools remain plugin responsibilities, may lose features and are not run by Core merely because metadata mentions them. No arbitrary converter command is embedded in Struct or executed through the save metadata contract. Independent files/install/restore/launch grants remain required for their actual effects.

This is a future-design reservation: document extensible optional descriptors now, but no save browser, thumbnail collector, memory-card parser, slot editor, converter, migration job or universal save-loading endpoint is required for this delivery. Unsupported operations remain explicitly unavailable; no successful placeholder endpoints. Existing save-profile/location/backup contracts remain the implemented API scope.

### 13. Multiple libraries and runtime/content identity

Libraries are named logical collections with a set of individually approved roots and watch flags, each with its own location/volume metadata and availability. Create/update/root mutation calls use expected revisions and user-approved directory handles. Deduplicate overlapping roots and aliases by canonical identity to avoid repeated observations; removing a root disables monitoring rather than deleting games or archives. Removing a library never recursively deletes its directories. Map existing multi-root watches into the API without resetting them or changing official provider implementations.

Runtime resources represent installed software capable of executing multiple content items: emulator, interpreter or compatible engine runtime. They include approved executable/version/platform, supported content types and structured argument templates. Registering a runtime does not download or install it. Each game has a stable logical id, separate installation/content paths (possibly several discs/files), its own title/match/playtime/save context and a reference to the shared runtime plus a per-game launch recipe. Never use only the runtime path or PID as game identity. The same runtime can run several distinct games; moving/updating a runtime does not merge those entries. Packaged standalone engine games can remain ordinary executable targets; runtime binding applies only when an external interpreter is actually needed.

Use the existing game.custom_launch contract to compose approved runtime/content handles and argument vectors; ordinary game.launch reuses the approved detected recipe without overrides. Runtime installation files, game content, prefix and saves can be on distinct volumes. Observe the launched game context, not merely the lifetime of a shared emulator: overlapping sessions remain distinguishable and an idle launcher does not automatically accrue playtime to all its games. Do not guess which game is active when the evidence is ambiguous; plugin activity reports are attributed evidence rather than authority to kill processes or restore saves.

#### Shared game identity, discovery and emulator migration

Use the GameNode game id as the canonical game reference once identified, with stable local game/content handles while matching is unresolved or offline. Preserve existing official provider keys and reconciliation. ROM files, variants and installations are subordinate resources, not the runtime's identity: paths/basenames are locators and hashes are content evidence. Moving or renaming a ROM does not create a new game; changed bytes can be a different content revision. Matching to one game must not erase platform/region/patch variants or assume their saves are interchangeable.

The same registered ROM and GameNode game discovered for ZSNES and bsnes appears as one game with multiple user-selectable runtime bindings, not one library entry per emulator. Discovery source provenance remains distinct. Runtime plugins may independently request library.discovery within approved roots. Games.RegisterContent accepts either the existing own-provider context or a negotiated scoped runtime-content context for extensions; the latter submits observations/binding candidates without impersonating another provider or receiving its context. Discovery alone grants no launch, runtime mutation, broad reads or file access.

DeSmuME-to-melonDS example: register melonDS, authorize selected existing content/runtime/profile reads, propose a binding change for the same GameNode game, review its effective launch plan, and preserve playtime, saves and backups. Reading old resources plus writing a new own binding need not grant deletion or mutation of the old runtime. Explicit foreign write/delete is needed only when actually changing those selected foreign records. Runtime removal never cascades into game/content/save deletion. Save compatibility/import/conversion is evaluated separately; retained history is not evidence of save-format compatibility.

#### Runtime-specific adapters and common playtime sessions

Detection is case-specific, but one plugin per emulator is not mandatory. One plugin can implement several adapters; independent specialized plugins are equally valid. Adapters use each runtime's capabilities and translate observations into a common typed lifecycle. Core owns validation, attribution and accounting, without emulator-specific detection logic. Documented interfaces can make an adapter small; boot failures, content switches, evidence loss and version differences still need tests.

Examples: RetroArch can expose loaded content and state through its enabled GET_STATUS interface; PCSX2 accepts a boot image and batch execution; Dolphin accepts an execution target. Launch arguments identify requested content, not confirmed successful gameplay or subsequent content switches. These examples illustrate optional adapter strategies, not emulator integrations required from Core. Sources: https://docs.libretro.com/development/retroarch/network-control-interface/#get_status, https://pcsx2.net/docs/advanced/cli/ and https://github.com/dolphin-emu/dolphin#command-line-usage.

Add a negotiated API 1.4 runtime-session event family over ProviderHost.Exchange, with correlated accepted/rejected outcomes. The independent game.sessions.report permission defaults denied and binds the authenticated plugin to approved game/installation/runtime scopes. Typed fields include content identity, runtime instance identity (not PID alone), session correlation, sequence, observed time and identified/started/paused/resumed/content_changed/ended/identification_lost transitions. Launch permission does not imply reporting permission; reporting grants no launch, raw process inspection or filesystem access. Extension plugins may report approved games without impersonating their provider. Descriptive GamePresence remains separate and cannot establish measured gameplay.

Core validates current context, sequence, timestamps and a documented finite freshness timeout, assigns session identity, and arbitrates reports against other reporters and existing process evidence to prevent duplicate accounting. The same process can close A and start B at a validated content boundary. Several instances of the same runtime remain independently attributable. Reused PIDs and runtime paths cannot establish content identity. A known host launch is a candidate binding; it needs gameplay confirmation before counting. Confirmed pause intervals are excluded. The manifest declares playtime/pause detection capabilities and, without pause detection, the developer selects disabled measurement or application-open accounting. Installation discloses the latter with: ‘Plugin incapaz de distinguir pausas no jogo, tempo de jogo aberto é contabilizado como tempo de jogo’. The user may disable this plugin's accounting during installation or in settings; preserve history and independent evidence from other sources. This mode counts pauses that cannot be detected but still requires identified game/content, bounded freshness and deduplication; shared-runtime idle time is not assigned to unidentified games.

On lost, stale, conflicting or revoked identification, or reporter disconnect, stop extending the interval at its last accepted observation and mark activity unknown. Fresh evidence starts a new supported interval without backfilling unknown gaps. Do not charge menu/idle time or infer current content after restart from a surviving PID. Preserve existing account, Store/Internal, counter, checkpoint and platform availability policies; these changes do not enable unsupported native tracking, authorize backup/restore or add remote measured-session submission. Shared projections use the applicable common category permission or the explicit sharing review for sensitive data; no process handles, credentials or launch tokens are shared. Plugin historical observation retention requires storage.persist; Core-owned measured-session history follows existing account storage rules.

### 14. Plugin-produced diagnostics, hardware, presence and performance

This delivery implements the data plane, with no dependency on immediate Core feature consumption. Producers collect and interpret data; Core validates schemas/limits/identity, receives, stores as authorized, and makes projected records available to approved other plugins. It does not run CrystalDiskMark/dd, SMART collectors, hardware scanners, game hooks/overlays, FPS capture or prediction algorithms. It also does not automatically send presence or hardware to GameNode servers/friends or change launch/backup behavior from a report alone.

StorageDiagnostics accepts benchmark and SMART reports. Benchmark fields include device/location, tool/version, timestamp, read/write and sequential/random mode, test size, block size, queue depth, concurrency, cache/direct-IO description, throughput in bytes/sec, IOPS and latency units. SMART includes health/temperature/wear/attributes when available, schema/source units and unavailable/unsupported/access-denied states. Reports are plugin claims, not independently verified disk-health certificates; publication permission does not authorize the test or native writes. Associate records with the observed volume/device token so a replacement disk does not inherit old metrics.

Computer.PublishHardware accepts versioned CPU/GPU/RAM/OS/driver observations and unknown/multiple-device states. Omit serials, machine names and unique hardware fingerprints from the standard schema; any extension carrying identifiers requires separate explicit field consent. A local computer-context id permits history correlation without disclosing a global machine id. A plugin can combine authorized hardware and game-performance history to compute its own predictions; Core need not implement that algorithm.

GamePresence.Publish/Clear reports bounded plain-text/localizable fields and typed extensions such as mode, map, ranked state, character and level, tied to an authorized game and session. Set sequence, observed/received time and bounded TTL (default 60 seconds, maximum five minutes); expire or mark stale on game/session end, producer disconnect, sequence regression or TTL. Validate attribution and never accept another account's identity from the payload. Presence expiry is not proof the game exited. No arbitrary markup, executable actions or mandatory public-profile presentation.

GamePerformance.PublishSamples/EndSeries accepts timestamped batches linked to original game/installation, computer context, gameplay session and optional launch/runtime recipe revision. Define FPS as an observation/window with collection method and average/min/max/percentile semantics explicitly identified; distinguish instantaneous values from frame-time-derived aggregates. CPU fields state process/system scope and normalization basis (whole-machine 0–100 or per-core convention); RAM is process working-set/resident bytes with OS/source semantics, not an unlabeled percent. Optional GPU/VRAM/frame-time fields are versioned, not prerequisites. Source/tool/version, sample interval, units, duration and quality accompany each series. Reject nonfinite/impossible data, retain gaps/dropped/out-of-order/duplicate sequence information and never convert missing samples to zero FPS. Attribution to a runtime PID alone cannot assign metrics to every game using it.

QuerySeries/Aggregate read only retained authorized samples with explicit time/window/resolution and provenance. Aggregates are computed over available samples and state coverage/gaps; no interpolation or prediction is presented as a measured observation. Historical collection is possible only with storage.persist and a retention budget. Initial payload limits: 1 MiB/report or batch, 1000 samples/batch, at most one performance batch/sec per plugin and 10 observed samples/sec per series; bounded queues return backpressure/dropped counts explicitly. Generic records and sample retention default to session-only until granted persistence; presence always expires and is not historical by default.

### 15. Default-deny inter-plugin data exchange

The public pool is local and distinct from private storage. Producers request publication permission; the user authorizes it. Consumers request independent read/create/update/delete permissions, selected explicitly during installation or in settings, scoped either to an entire published category or individual records. Category grants include eligible published records within scope; selected-record grants do not widen automatically. Durable publication additionally requires storage.persist. Shared mutation preserves creator provenance, records the acting plugin and checks expected revisions. Private namespaces and foreign provider facts remain excluded. These shared grants are an alternative authorized resource scope for domain operations, not a requirement to possess own-record access to another creator's records. Query category selectors select data; they never grant an operation.

Pair every shareable data-ingestion family with typed Get/List/Watch access; use domain catalogs for resources and a common Data broker for custom/sensitive datasets. Do not force domain clients to use Data APIs or create source-to-recipient links for ordinary authorized resource lookup. This includes library/root declarations, provider discovery/catalog and non-secret account observations, metadata/artwork references, launch/runtime recipes, save profiles and inspection results, storage diagnostics, hardware, presence and performance. Queries are views of validated domain datasets, not an unrestricted mirror of raw RPC payloads. Generic commands such as Secret/Login credentials, cookie values, marked-secret configuration/environment values and Core authentication remain non-shareable; administrative mutation calls do not become executable by subscribing to their results.

Every published envelope carries dataset/schema version, resource context, source observation time/sequence and host-assigned provenance: authenticated plugin id, declared developer/name, origin/install source, publisher key fingerprint, exact installed version and package digest, received time and expiry. Host-derived datasets name Core/version as source. A client cannot impersonate another producer by supplying provenance. Names/developer strings are declarations; publisher fingerprint verifies package continuity, not real-world identity. API source identity remains independent of the game provider identity.

All third-party data permissions are disabled by default and are presented for selection during plugin activation. Define common shared-data permissions by category, including game-path read and performance-history read; granting one authorizes queries to all published records in that category within its declared resource scope, regardless of publisher, without separate source-to-recipient approval. Sensitive/custom datasets retain explicit sharing review. The host returns only the category's declared projection. A new category or broader scope requires its own permission and user grant. A read permission does not authorize publication, mutation, or durable recipient copies. Secret data, credentials, cookies, tokens, marked-secret configuration and Core authentication remain outside all shared categories and continue through isolated APIs. Core publishes no user data to plugins merely because it holds that data.

The permission belongs to the consuming plugin and is selected from the plugin's requested, host-supported grants during activation; it covers eligible publishers without requiring the consumer to enumerate each source. Permission metadata identifies the category, read operation and bounded resource scope so the activation UI can explain the resulting access. A grant permits use but does not initiate queries or deliver data automatically. Every query/list/watch operation that can include common records carries a typed `common_data_categories` selector listing the categories requested for that operation; omission or an empty list excludes common records. Every listed category requires the caller's current grant. A missing grant denies the common-data request without changing access to the caller's private namespace. Results preserve producer provenance, and the host does not merge common records into a plugin's private records. The same permission remains subject to current session/profile scope and revocation. A plugin update that newly requests a category or broader resource scope requires user review; an already granted category does not acquire unrelated categories. A publisher may query its own submitted data within its publish scope. Delivery uses authenticated host transport, never arbitrary plugin endpoints or a public broadcast socket.

Revocation immediately fences new queries, stream delivery and queued records; invalidate consumer cache tokens/cursors on changed projections and send a safe revoked control result. Default subscriptions start at the current cursor with no backlog unless the granted category includes history or history is separately approved. Display that already delivered copies cannot be recalled from unsandboxed native plugins. Do not create forwarding loops: records retain origin/derivation lineage, recipient projections and idempotency ids, and grants cannot be widened by republishing. Derived datasets keep protected origin tags; common-data onward visibility follows the recipient's applicable category permission, while sensitive/custom data retains explicit onward-sharing review. Metadata enforcement cannot prevent native code laundering data outside the API; retain the honest native-access disclosure.

Domain catalog example: the user grants B a category read permission during B's activation. A calls Runtimes.Register; B calls Runtimes.List/Get/Watch and names the runtime-catalog category in `common_data_categories` to see records published by A and other plugins within the permission's declared catalog scope, with original provenance. B needs no pairwise A-to-B agreement. Runtimes.Update/Remove require own-record or explicitly authorized public-pool mutation scopes; read permission grants no mutation. Read access remains opt-in per consuming plugin, never a global installation default. A producer may not downgrade private metadata into catalog visibility.

Apply common category permissions to records explicitly designated common, including game paths, performance history and runtime/content availability catalogs, plus other domain catalogs when declared as common. Game paths can be shared only through their declared game-path projection and resource scope; file contents, secret-bearing argv/environment and private extension fields remain excluded. Metadata or launch recipes without a named query method are retrieved as projected fields on Library.Get/List/Watch or typed catalog objects, not via invented new sharing RPCs. For ROM availability, add an optional typed runtime-availability projection to Library.Get/List/Watch. It joins content identities with runtime availability observations by stable console/platform identity and returns the reporting runtime and observation freshness. It represents what a plugin reported as available, not a compatibility guarantee; it returns no absolute path or file bytes. The caller names the runtime/content-availability category in `common_data_categories` and holds the relevant grant to receive other publishers' observations. Sensitive datasets such as diagnostics, hardware, presence or custom Data retain explicit sharing review unless a category is deliberately designated common. Unknown schemas and fields never inherit access merely because another category permission was granted.

Activation UI names each requested common-data category, its read scope, representative data and whether it includes history. It explains that the grant only allows access; the plugin chooses per query whether to include common records, with private-only as the default. Sensitive/custom-data review continues to identify its source, recipient and projection. Effective access is consistent across Data and domain query methods: no alternate alias can bypass a missing category grant or sharing review. Provenance remains visible on returned records, but common-category access does not require pairwise publisher approval. Revocation fences later queries and delivery, while already delivered copies cannot be recalled from an unsandboxed plugin.

### 16. Consented persistence, history accounting and cleanup

Introduce independent storage.persist, default denied and selectable separately from category read permissions during activation. It supplements a publish/write/read grant rather than implying those grants; granting it does not grant access to another category. Requests explicitly select SESSION_ONLY or PERSIST and return actual durability, expiry and owner; a denied persistent request returns PERMISSION_DENIED, never silently switches to volatile success. Session-only publication and storage writes remain possible when explicitly requested. UI explains the retention policy and that revocation stops new reads but cannot automatically recall copies already delivered to a plugin. Private secrets continue through existing scoped Secret service, not this generic data store; game/save files and backup archives are not plugin data to be garbage-collected here.

Store managed durable plugin data under data_dir/plugin-data/<publisher-fingerprint>/<plugin-id>/, with versioned metadata and per-owner payload/index accounting. Canonical published records are charged to the producer; a recipient's durable projected copy is charged to that recipient and requires storage.persist plus its configured retention policy. These controls are independent of category read permission. Track copied/derived source provenance and distinguish source-copy deletion from recipient-copy deletion. Default total managed quota is 64 MiB per plugin (including existing 16 MiB private-storage quota); the user can set larger budgets and retention periods. Check quotas before commit, return resource exhaustion without corrupting history, and never let a plugin grant itself a higher budget. Game-performance retention can prune oldest unprotected samples under the user's explicit retention policy while reporting its retained interval and gaps.

Offer host UI usage by plugin/source/version, dataset/category, logical payload size, physical managed size including indexes, quota, last write/read, retention and exact local path. Use worker-side accounting and identify shared overhead estimates instead of pretending per-record physical bytes are exact. Give plugins access only to their own logical usage and entry identifiers. Only host-owned user administration can reveal exact physical paths, view global usage or delete another namespace. Plugin responses, errors, job metadata, logs and events never disclose managed-persistence paths. The SDK exposes no filesystem path accessor for this store. Third-party unmanaged native writes are outside these measurements and quotas.

Uninstall explicitly offers keep or delete managed persisted data, showing plugin ownership, path, size and active consumer dependencies; default to keeping until the user chooses. Keeping leaves an inert archived dataset namespace with provenance, not executable code or active grants. Same-id/same-publisher reinstall can reclaim its data after normal activation/permissions; another plugin can read archived common-category records when its current category grant covers them, while archived sensitive/custom records require fresh explicit sharing review. Deleting removes only the selected managed namespace/copies and indexes, invalidates relevant query/history tokens and emits authorized deletion events. It never deletes game installations, live saves or backup archives; it cannot recall copies retained outside the host.

The storage.persist grant also permits a plugin to list/delete its own logical persisted entries, clear its namespace and configure an automatic retention/cleanup policy within the user-granted limits. It needs no separate foreign-filesystem authority. Caller ownership is derived from authenticated identity, never a request plugin-id/path field; pagination, entry ids, cursors, job ids, selectors and policies cannot address any other namespace. No physical path is accepted or returned. Cleanup rechecks ownership at commit and performs bounded transactional removal through the host; plugin-defined executable cleanup hooks are prohibited. Even a user-approved generic Files root cannot bypass this namespace boundary: all host-managed persistence directories are reserved/excluded from plugin filesystem/path-inspection APIs. The prohibition applies to persistence/cleanup; separately authorized game/save/install/restore APIs retain their existing domain scopes. Native unsandboxed processes can still bypass host APIs; this is an API isolation guarantee, not OS confinement.

Provide user-reviewed cleanup by uninstalled/disabled/unused plugin, age, dataset and size/quota thresholds. Show preview, local path, size estimate and affected consumers; offer per-plugin/category deletion and retention rules, preserving any user-protected records. Automatic cleanup defaults off. A plugin can opt into a policy for its own namespace only after storage.persist is granted, within user-set retention/protection/budget limits; host-wide cleanup requires separate explicit user policy. Neither policy can delete another plugin's entries through a plugin call. Transactional deletion must coordinate with writers/readers and preserve unrelated plugin data; active jobs receive an explicit data-removed result rather than reading half-deleted history. Last-use metadata describes actual host access, not a guarantee that external copies no longer exist. Cleanup and sharing UI are required administration features; analytic dashboards remain future consumers.

### 17. Per-game file authority and native-process limitations

At installation all third-party grants are disabled, including read/write access. Each file grant binds publisher/plugin identity, current authorization revision, an explicit game id/installation or save-context namespace, approved roots and allowed operations. Write does not imply delete or access to another game. An approved library parent directory for discovery does not grant file mutation across its games. Reject root escape, sibling namespaces, remounted foreign volumes and any reserved host/plugin-persistence directory even when reachable under an otherwise approved parent. Shared emulator resources require visible approval for the complete affected-game scope; no silent widening from one game to a whole memory card.

Enforce these boundaries in host service authorization and at commit. Other separately authorized install/restore/tool operations retain their own scopes and confirmations. Permissions are contracts for GameNode API access, not promises that external native processes cannot perform direct OS operations. No sandbox is required by this change, and no permission label or missing physical-path response can be advertised as OS confinement. The Core validates/authenticates its services and owns its managed data, while users choose third-party executables with clear source/version/access information.

### 18. Per-endpoint typing and extensible catalogs

This section is the field-policy inventory for every existing and proposed RPC. Route spelling for new services is a planning proposal under package gamenode.plugin.v1 (minor 1.4 does not rename the package). Existing eight RPC names/field numbers remain compatible. No implementation/proto file is changed by this document. Entries are individual methods, not new HTTP/REST endpoints. Shared-resource read is distinct from private dataset export, and both are disabled until user authorization.

**Use typed contracts when Core must interpret a value to authorize, execute, filter, account or compare:** identities, ownership/provenance, permissions/scopes, version, revision/preconditions, handles, pagination/cursors, timestamps/durations, byte counts/quotas, statuses, errors, TTL, filesystem selection rules, URI/executable targets, argv/cwd/env, retention selectors and standardized metrics/units. Use explicit presence for unknown/missing observations; preserve precise int64/uint64 and timestamps outside Struct. Free-text descriptions never substitute for a typed denial/status or grant.

**Use hybrid resource/report records for extensibility:** a typed stable base plus explicitly designated `map<string, ExtensionPayload> extensions`, where map keys are owner-controlled reverse-domain namespaces. The typed ExtensionPayload envelope contains schema_id, schema_version, schema_digest and google.protobuf.Struct data. Producer/developer/origin/version/provenance are assigned by the host outside the Struct. Domain clients use normal Register/Update/Get/List/Watch calls to exchange these records; no separate A-to-B endpoint is necessary. Extensions can describe vendor metadata, recommendations, game modes or plugin-specific annotations. Core stores/filters them without executing their semantics. Core-recognized behavior must use the typed base or a new negotiated typed feature.

**Use opaque bytes for actual content:** file contents, artwork, HTTP bodies, secrets and private application storage are bytes inside typed bounded envelopes. A blob may contain a plugin's JSON/Protobuf, but Core does not turn it into a generic command, arbitrary host configuration or shared record. Secret bytes remain non-shareable. Data.Publish is the deliberately extensible custom-dataset route: a typed dataset/resource/version/durability envelope with declared Struct payload and fixed data.publish permission scoped to that dataset; built-in domains such as runtime registration cannot be emulated through it to bypass validation.

Schemas are declarative versioned assets in the signed plugin package, discoverable through DescribeApi descriptors, not executable UI/code or remotely fetched schemas. Validate a bounded JSON-Schema subset without external references. Core understands structural types/field classifications, not plugin semantics. A schema unrecognized by a consumer can still be retained by the host as declared data, but its fields are not automatically shared or interpreted. Reject data inconsistent with its declared schema. Unknown/new optional namespaces do not invalidate an otherwise usable typed record; omit them from unauthorized projections and show unsupported extension information when needed. Never silently reinterpret an unsupported required executable feature as metadata.

Set initial extension bounds to 32 namespaces and 64 KiB encoded extension data per resource/report, depth eight and 256 total object keys, also bounded by the enclosing message/batch limits. Reject nonfinite numbers, duplicate/colliding namespace definitions and protected-key shadowing. Struct numbers are double precision, so exact large identifiers/counters belong in typed fields (or declared string fields inside an entirely custom schema), not implicit floating-point numbers. Do not use Any, remote type URLs, unknown protobuf fields, opaque JSON command strings or arbitrary extension RPCs as the default extensibility mechanism. Core-generated bindings may discard unknown wire fields; supported extension maps are known fields whose unrecognized application keys must be retained explicitly.

Updates carry expected_revision and typed field masks/extension namespace patches. Patch only fields allowed by the authenticated plugin's own-resource or explicitly delegated domain-write grant, retaining extension namespaces that an older client did not select or understand. Reject unauthorized namespace changes, all creator-provenance forgery and action changes lacking their own validated approval. A read-only B cannot change A's runtime by resubmitting a full record. Resource identity is host-issued and stable; delete/re-register or stale revisions cannot seize an existing resource. Adding metadata never grants access to its executable/root or another dataset.

Runtime example: A registers typed id/name/version/executable_ref/supported_formats and an org.example.compatibility extension; user-approved B uses Runtimes.List/Get and optionally reads that namespace. A runtime's executable selection and argv template are still typed. A recommendation field such as preferred_proton cannot change launch behavior by itself; a plugin must translate it into an approved typed custom-launch recipe.


Illustrative new resource schema (planning example; final field tags are assigned during implementation, not applied to legacy messages):

```proto
message ExtensionPayload {
  string schema_id = 1;
  uint32 schema_version = 2;
  bytes schema_digest = 3;
  google.protobuf.Struct data = 4;
}
message RuntimeRecord {
  string id = 1;
  string name = 2;
  string version = 3;
  ExecutableRef executable = 4;
  repeated string supported_formats = 5;
  map<string, ExtensionPayload> extensions = 6;
  ResourceRevision revision = 7;
  SourceProvenance source = 8;
}
```

ExecutableRef, ResourceRevision and SourceProvenance are typed domain messages; they cannot be replaced with keys inside extensions. Struct is nested only in ExtensionPayload. A custom metadata schema may add fields without changing RuntimeRecord; a new kind of Core-controlled execution still requires a negotiated typed contract.

### 19. Launch-plan review for every execution customization

Apply one common review to all GameNode-mediated execution customizations: runtime/interpreter/emulator changes, alternate executables or URIs, wrappers, mod loaders or declared launch-time mod layers, argv, working directory and environment additions/changes/removals. This includes customization configured by a user or a host-managed integration, not only changes labelled as third-party custom launch. Keep unchanged official default launch behavior as the baseline; no official plugin implementation change is required. Mods merely installed on disk are not automatically discoverable by the host. Acknowledge that the reviewed component list covers known/declared launch components, not every library or subprocess the executable may load later.

Build a typed immutable LaunchPlan on the host from the validated effective recipe after resolving runtime/content/resource handles, selected mod layers, parameters and current grants. Never use the plugin's friendly description as the execution preview. Include game/installation/profile, requesting plugin and package version/digest (or local-user source), contributing resource/component owners, declared developer/origin/publisher, recipe/base revisions, resolved executable identity, ordered intermediaries/runtime/content/mod components, URI and resolved handler when available, argument vector, working directory and exact environment delta. Unknown URI handlers or component versions are displayed as unknown rather than certified. Reject unsupported target semantics before constructing an executable approval.

Use a host-owned shared AppModal named Launch plan / Plano de lançamento for the decision, with a substantial scrollable detail surface using existing modal components where necessary. It must remain keyboard accessible, localized en/pt-BR, responsive and safe for untrusted text. The initial summary names the game, source and effective change (for example a different runtime or mod loader). Show differences from the detected default and the previously approved plan, with full paths/URI, every argument separately, execution order, known mods/loaders, cwd and set/changed/unset environment keys and values. No ellipsis-only executable paths or hidden trailing arguments. Make control/bidirectional characters visible in a literal escaped representation without changing what the actual argument means. A reconstructed command line may be provided for user inspection, but it is not the shell string passed for execution.

Separate host facts from Plugin-provided explanation. Local launch detail views may expose user-authorized secret values only through an explicit reveal control; their keys, presence, destination and change must remain visible without logging/persisting/exporting raw secret values or unrelated inherited environment. If a secret-backed argument/environment value changes, renew approval using a host secret revision marker rather than disclosing its contents. Show risk-relevant known changes, such as a new runtime, mod loader, code-loading environment or URI scheme, without claiming heuristic risk labels exhaustively identify dangerous behavior.

Offer Cancel as the safe default, Run once and optionally Authorize this recipe for this game. A one-time approval is an expiring single-use host token. Remembered approval is scoped to the exact game/installation/profile, requesting plugin identity/version, contributing component identities, grant revision, recipe/base revision and effective executable/URI/runtime/mod/argv/cwd/environment plan. It never authorizes all games or all future recipes from that plugin. Store a versioned canonical plan fingerprint with explicit field encoding; do not hash ordinary protobuf/Struct serialization or persist plaintext secrets as the approval key.

RequestCustomLaunch and all host paths that apply an execution customization redeem only the host-issued plan/approval identity. Acknowledge/approve the displayed plan, not a replacement payload supplied at execution time. Re-resolve/revalidate resource identities, current policy and all plan-bound fields immediately before dispatch on workers; replacement, changed inputs, revoked grants, plugin/component version or target changes invalidate the corresponding approval. A plugin cannot display a benign plan and then submit different argv, environment or executable under that token. If resolution becomes stale or fails, show the changed plan or actionable error; never silently launch another route. Repeated user Play for an unchanged remembered-approved plan needs no second prompt. Plugin-initiated execution still needs a correlated user intent, even when a recipe was previously approved.

Reject requests outside the API contract before the dialog. Unsupported shell execution, elevation, invalid scopes, unapproved resources and metadata attempting to supply executable policy do not gain an Execute anyway button. The prompt is user consent within the supported contract, not an override of access controls. This does not promise that an approved native executable is benign: its own code and accepted arguments can still have effects the host cannot infer. No sandbox is added by this design.

Use a concise localized disclosure, for example: GameNode checked the scope of this request but does not certify the behavior of the programs executed. They may perform operations with your user's privileges. Do not use safe/certified language or a successful signature/hash check as an executable safety verdict. Package provenance, executable identity, plan validation and the plugin's explanation are distinct facts. Existing non-sandbox disclosure remains applicable to native operations outside the API.

Mod installation or file modifications require their own scoped operations/confirmations; approving a modded launch does not grant files.write, tools.apply or restoration permissions. Conversely, installing a mod does not approve a changed runtime/launch plan. SDK and direct clients share this same review/approval protocol through typed plan/result fields on the existing launch methods; no plugin-controlled confirmation UI or dynamic Struct command channel is introduced. Both examples and acceptance fixtures must cover emulator/runtime, mod-loader and custom-parameter cases plus rejected or changed plans.

Reference rationale: https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html . Parameter separation and validation address command/argument injection boundaries; they do not certify arbitrary executable behavior.

## Risks / Trade-offs

- Native plugin can bypass API restrictions or alter same-user files → explicit consent/disclosure; API checks still protect cooperative calls and prevent confused host authority, without claiming OS confinement.
- Broad initial API adds maintenance cost → fixed matrix, typed domain adapters, conformance fixtures and per-method risk/scope metadata; no universal invoke RPC.
- Signing may look like safety certification → fingerprint trust separate from integrity, clear labels and no automatic publisher trust.
- Revocation races and failed updates → grant revision checks at commit, job fencing, durable transactions and fail-closed recovery.
- GPL/MIT boundaries may include contributor code → provenance review before MIT distribution; retain GPL host internals and notices. Reference: GNU GPL FAQ on separate programs, GPL libraries and contributor permission; this design is not an automated legal finding.
- Shared host changes affect official integrations → additive messages/paths, unchanged descriptor baselines and official conformance regression checks.

## Migration Plan

1. Freeze official descriptors/grants and API 1.1–1.3 fixtures; add additive 1.4 contracts and isolated external registry migrations with no external auto-registration.
2. Deliver persistence/package validation and host policy before exposing install/enable UI; no third-party executable runs merely because a directory exists.
3. Wire scoped Core adapters and lifecycle/update recovery; then settings, public distributions and both examples.
4. Validate Linux and Windows transport, filesystem/credential/process behavior on their native OS. Mock UI and Rust/Go fixture checks complement rather than replace native acceptance.
5. On application rollback, ignore unknown third-party state safely and keep official providers working. Retain external packages/state for recovery; never auto-execute them through a legacy path. Plugin-version rollback follows section 6.
