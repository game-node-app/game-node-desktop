# Design

## Boundary and dependencies

This follow-up depends on the MVP's authenticated plugin identity, profile fencing, permission revisions and package lifecycle. The generic verified-package import, activation lifecycle, manifest permission replacement and requested/granted/effective permission inventory remain owned by `add-third-party-plugins` tasks 10.2 and 10.4. This change consumes those foundations and owns the shared-data-specific policy UI, persistence and enforcement; it does not duplicate package lifecycle or generic permission administration.

## Shared data

Keep plugin-private storage separate from published datasets. Attribute every record to a host-derived owner and package provenance. Queries and subscriptions use explicit per-query selectors and default-deny category/record grants. Apply projection, size/depth limits, cursor fencing and revocation to every delivery path.

Connect the activation review's common-category and selected-record choices to the persisted `SharedSharingPolicies` store. Resolve the policy key from the host-authenticated plugin, publisher fingerprint and active profile; never accept those identity parts from plugin RPC data or an unverified UI value. Start with empty grants. Persisting a grant only makes matching records eligible: each query still needs its explicit selector, and saving the grant must not run a query or deliver records.

Keep sensitive/custom sharing separate from common category grants. The host review must identify the exact source, recipient and dataset, and the allowed fields and history/live delivery modes. Persist the decision through `SharedSharingPolicies`; a common-category grant cannot widen it, and plugin RPC cannot create or expand it. Revocation updates the policy revision and fences queries, cursors, queued events and subscriptions. Recipient retention remains a separate consent governed by the Persistence work; a read or sharing policy never grants durable storage.

The data-specific review controls build on the generic plugin activation and permission inventory work in `add-third-party-plugins` 10.2/10.4. Policy writes from Tauri must be asynchronous and move filesystem persistence off the UI thread. Task 1.5's producer/consumer contract is verified only after this integration provides a user-authorized public flow.

`DataListReply.revision` carries the global broker revision of the returned snapshot. A client passes that exact revision to `DataWatchRequest.after_revision`; the host accepts only a current resumable position and fails closed for stale positions, so the list-to-watch handoff cannot skip intervening records.

## Performance history ingestion and queries

Implement GamePerformance as a typed adapter over the session-retained DataBroker. The plugin supplies FPS, CPU and memory observations plus collector/source, tool name/version, declared sample interval, runtime and recipe revision, and explicit units (`frames/second`, `percent`, `bytes`). The host binds each series to the authenticated plugin/publisher/profile, active session, selected game and installation, and its own local `active-host` computer context. `computer_id` from the plugin is rejected. A runtime ID is descriptive attribution only; it does not prove process ownership or start collection.

An `observed_at` sample timestamp is Unix milliseconds so the contract can represent its minimum 100 ms interval at 10 samples/second. `sampling_window_ms` is zero only for instantaneous FPS; frame-count-window and frame-time-derived FPS require a nonzero window at least as wide as the declared sample interval. Each sample identifies instantaneous/average/minimum/maximum/percentile FPS semantics and measured-versus-estimated quality. Percentile samples carry their percentile rank; optional minimum/maximum values bound the reported observation. CPU scope is process or system, with either whole-machine percentage (0–100) or per-core percentage normalization. Memory identifies working-set or resident bytes and names the source/OS basis.

Reject unknown units/enums, non-finite or impossible values, wrong selected-game identity, timestamps too far in the future, windows outside 100–600000 ms, batches above 1000 samples or 1 MiB, non-increasing sequences, and samples faster than the declared interval. Sequence gaps remain visible as dropped-sample coverage and are never filled with zero. A duplicate of the latest batch is idempotent; a duplicate or out-of-order earlier sequence conflicts. Limit each authenticated plugin to one accepted batch per second; return explicit backpressure and dropped/retry counts when rate or retention limits are reached. Retain at most 1 MiB per series in the bounded in-memory broker, tied to the publishing session; disconnection removes it. This task does not enable persistent retention—storage.persist and its independent retention controls remain separate.

List returns retained series within the authorized query and cursor scope. QuerySeries filters actual samples by the requested millisecond interval and optional resolution; resolution keeps actual observations and never interpolates. Aggregate accepts FPS, CPU percent or memory bytes and average/min/max or nearest-rank `p0`–`p100`, reporting units, sample count, source provenance and sequence-gap coverage. Every cross-plugin query/watch uses the explicit common performance-history selector and the current sharing policy; the category grant does not itself select records. Watches recheck session permission and policy revision and terminate on revocation or queue overflow. No handler adds capture hooks, prediction, persistent history or Core-owned game instrumentation.

## Emulator-backed shared save resources and backup coordination

Treat an emulator-backed memory card or other shared save resource as one host-managed resource referenced by multiple existing GameNode game/installation identities. A plugin may propose the resource identifier and bindings, but the host resolves them against the authenticated plugin, registered runtime/content bindings, active account profile and already-approved file/folder handle. Never accept a backing path or the affected-game set as authority from plugin RPC data. Keep each game's identity, history and ordinary save profile independent.

Before creating or changing a shared-resource scope, the host presents the complete affected game/installation set and the backing resource's approved location description for explicit user consent. Persist that decision against the authenticated plugin, publisher, profile, resource identity, exact normalized affected-game set and resource/profile revisions. Any change to the backing handle, runtime binding or affected-game set invalidates the approval and requires a new review. A plugin mutation cannot silently widen scope, and ordinary `saves.*` grants or a prior per-game profile approval do not substitute for this review.

Coordinate use through a host-owned resource coordinator. GameNode-supervised runtime launches acquire a host-issued use lease for each shared resource and release it only after the supervised process tree exits or is fenced. Backup/restore acquires an exclusive operation lease and rechecks the host-observed active-use state before touching files; in the initial implementation, neither backup nor restore runs while the resource is active unless a separately verified runtime snapshot operation is available. The host also checks externally started processes against the exact approved runtime executable identity using platform process inspection. Plugin-reported game/session activity is descriptive evidence only and MUST NOT authorize a restore. If process state is unknown or cannot be inspected, fail closed with an actionable busy/unknown outcome. A restore lock prevents a new supervised runtime launch from acquiring the resource until the operation commits or aborts. Never infer that the resource is idle solely because a plugin report expired or a process name matches.

## Typed-resource extension validation and projection

Extension payloads are bounded annotations beside a typed resource, never sources of identity, permissions, file access or execution. Validate the complete extension set as one unit: at most 32 namespaces, 64 KiB encoded payload bytes, depth eight and 256 total Struct object keys across all namespaces. Reject malformed envelopes, protected root fields, non-finite numbers and namespace/schema identity mismatches before persistence.

Resolve schema descriptors from the active package's integrity-verified `schemas/` assets in its signed manifest, bound to the host-authenticated plugin and publisher identity. Do not accept a descriptor or field classification supplied by a runtime RPC. Encode manifest SemVer in `schema_id` as `<namespace>.v<lowercase-version-with-non-alphanumerics-normalized-to-hyphens>`; `schema_version` is `1` for this mapping and `schema_digest` is SHA-256 of the exact signed asset bytes. Convert each packaged schema deterministically to field paths and classifications; validate the descriptor and payload shape before using schema fields for projection. Treat extension schemas as optional annotations: when a schema is unsupported, preserve its bounded payload opaquely for owner round-tripping and keep the typed base resource usable. Never project an unknown namespace or interpret its fields. For known schemas, common catalog projections include only declared public fields; sensitive/custom fields additionally require the exact source/recipient/dataset policy and field grant.

Register/Update and Get/List/Watch use the same validation and catalog resolution. A valid optional extension that cannot be interpreted must not make the base resource unreadable. Omitting an unsupported namespace from a projection does not delete it from the owner record.

## Persistence and administration

Durable records use a logical owner namespace and explicit retention choice. Quotas, cleanup and uninstall retention operate only on the authenticated owner's data. Host administration may report physical usage, but plugin IPC never receives physical paths. Diagnostics and gameplay observations remain plugin-produced data; Core does not add collectors or dashboards here.

## Updates, downgrades and private data

An update feed cannot select a release below the active version. A user-requested downgrade uses the same signature, integrity, target and API verification path as an update, shows the active and target versions with a downgrade warning, and changes the active package only after explicit confirmation. A publisher-key change requires a separate re-trust review bound to the exact new fingerprint; approving a package update does not substitute for that review.

The private-data owner namespace remains stable across package versions and continues to use the authenticated plugin, publisher and profile identity from the namespace resolver. A plugin that changes a private-data schema writes to versioned logical keys or schema identifiers. It does not automatically migrate destructively or delete the older values; retaining them allows a compatible last-known-good version to recover its data. Package rollback keeps the current grants intersected with the selected version's manifest. Reuse of data archived by uninstall remains a separate host-reviewed operation and does not grant a new consumer access.

## Publisher key change and data migration

A changed publisher fingerprint creates a distinct security identity even after explicit re-trust. Keep old data isolated and inert until the user reviews and explicitly requests migration of compatible data. The host previews source, destination and eligible data, checks schema compatibility and reports conflicts or partial failures; preserve old data and provenance until separately deleted. Never migrate secrets or grants automatically; access and retention require their own current approvals. This is separate from ordinary version upgrades under the same pinned identity.
